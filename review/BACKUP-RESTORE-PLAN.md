## 備份範圍

| 類別 | 必須保留的內容 | 驗收方式 |
| --- | --- | --- |
| 資料庫 | 業務資料、Auth 使用者、schema、RLS、授權、函式、trigger、migration 記錄 | 在獨立還原目標檢查結構、關聯與權限，再跑真實兩帳號測試 |
| 照片 | collection-photos、trip-covers 的實際檔案與路徑、大小、雜湊、必要 metadata | 從獨立檔案備份還原合成 PNG，核對 SHA-256，再驗證本人可讀、他人／公開 URL 不可讀 |
| 設定 | Auth Site URL／允許返回網址、寄信設定、儲存桶公開性、環境變數名稱、排程與外部整合 | 與已審查清單比對；秘密值只從受保護的秘密管理來源恢復 |
| 程式 | 已驗證的 Git commit、lockfile、Next 修補、GAS 來源與部署版本 | 固定 commit 建置／測試；不把測試憑證提交儲存庫 |

Supabase 官方說明：資料庫備份包含 Storage 物件的 metadata，**不包含實際照片檔案**。不能以 DB 還原成功推定照片也能恢復。

## 實際演練步驟（尚未執行）

1. 確認目前方案的備份能力與可用備份。免費方案不能直接假設有付費方案的每日自動備份；依官方方式規劃定期匯出與異地保管。任何新增付費資源先確認實際費用。
2. 明確指定新的隔離還原目標，保留來源唯讀。不得把正式站或目前共用測試 project 當作可直接覆蓋的還原沙盒。
3. 建立合成 fixture：兩個專用帳號、旅行、商品、收藏、行程、預算、支出、封面與一張 PNG。保存列數、關聯、預期內容與檔案雜湊作為比較基準。
4. 以適合目前方案／版本的正式備份方式備份 DB，並獨立備份照片。備份加密存放在受保護位置；原始 dump、使用者資料、密碼雜湊與秘密不得放到公開 GitHub／聊天室。
5. 只在隔離目標還原，記錄開始／完成時間與錯誤。核對資料、外鍵、RLS、grant、trigger、bucket private 設定與照片雜湊。
6. 重跑兩帳號直接 API 讀寫隔離、匿名拒絕、照片讀取／簽署拒絕、版本競爭及應用程式登入流程。防止測試環境寄出正式郵件或呼叫正式 GAS。
7. 特別核對 shopping_items.revision：一般 INSERT API 會觸發初始 revision=0，不能拿逐筆 API 匯入當作保留歷史版本的完整備份還原。使用經核對的 DB 還原程序，並規劃重新驗證／清除舊頁面狀態，避免舊客戶端版本碰撞。
8. 產出實測報告，列出備份時間、照片範圍、還原耗時、權限測試與未覆蓋項目。演練完成前不勾選「備份還原驗收通過」。
